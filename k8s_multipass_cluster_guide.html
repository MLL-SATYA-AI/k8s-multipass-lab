Build a 3-node Kubernetes cluster on Multipass

With the VirtualBox driver, every VM Multipass creates gets the same NAT address, 10.0.2.15, so by default the nodes can't reach each other. This guide fixes that: it walks through installing VirtualBox and Multipass, gives each VM a second, bridged network, pins every VM to a static IP so the cluster survives restarts, and builds the cluster on that.

Install prerequisites

Windows host

Three tools go on the Windows PC before step 1. Install them in this order — VirtualBox has to be there first, because Multipass's installer looks for it and offers it as a driver.

1. VirtualBox

Multipass uses VirtualBox as its hypervisor on Windows. Download the Windows installer and run it, accepting the prompts to install the network adapter drivers — those are what let the bridged network in step 1 work.

virtualbox.org/wiki/Downloads

2. Multipass

Download and run the Windows installer. It should detect VirtualBox and set it as the default driver automatically.

canonical.com/multipass/install
PowerShell — confirm the driver
multipass get local.driver
multipass version

The first command should print virtualbox. If it prints hyperv instead, switch it with multipass set local.driver=virtualbox (only works before any VM has been created).

3. kubectl

Not needed until step 9, but it's a one-line install, so get it out of the way now.

PowerShell
winget install -e --id Kubernetes.kubectl
kubectl version --client

Open a new PowerShell window afterwards so kubectl is on your PATH. Step 9 covers pointing it at the cluster once it exists.

Create the VMs

PowerShell on Windows

Launch one controller and two workers. The --network Ethernet flag adds the second, bridged interface, and it can only be set when the VM is created. Use lowercase names because Kubernetes node names must be lowercase.

PowerShell
multipass launch --name controller-001 --cpus 2 --memory 2G --disk 20G --network Ethernet
multipass launch --name worker-node1 --cpus 2 --memory 2G --disk 20G --network Ethernet
multipass launch --name worker-node2 --cpus 2 --memory 2G --disk 20G --network Ethernet
multipass list

Accept any Windows prompt about bridging. Afterwards, multipass list should show two IPv4 addresses for each VM.

Check the network

PowerShell on Windows

Find the controller's real address on enp0s8, then ping it from both workers. Kubernetes can't work until this succeeds. These addresses come from DHCP and can change, so the next step makes them permanent.

PowerShell
multipass exec controller-001 -- ip -4 addr show enp0s8

# use the controller address printed above
multipass exec worker-node1 -- ping -c 2 <controller-IP>
multipass exec worker-node2 -- ping -c 2 <controller-IP>
What you should see
2 packets transmitted, 2 received, 0% packet loss

Stop here if a ping fails. See Troubleshooting.

Set static IPs

All 3 VMs

Windows hands out the VMs' bridged addresses by DHCP, and they can change after a restart. Kubernetes bakes the controller's address into its certificates and config, so a new address breaks the whole cluster. Pin each VM to a fixed address before you build anything.

Work out your own subnet

There's no fixed subnet for this step — it depends on how your PC or router hands out addresses on the bridged network, so don't assume 192.168.137.x. Use the address step 2 printed for enp0s8 on the controller: keep everything except the last number. For example, if step 2 showed 192.168.137.63/24, your subnet is 192.168.137.0/24 and you'll pick host numbers like .101–.103 inside it. If it showed 192.168.1.40/24, your subnet is 192.168.1.0/24 instead, and so on — common ranges are 192.168.x.0/24, 10.x.x.0/24 or 172.16–31.x.0/24, all with Windows Internet Connection Sharing supplying /24.

You're choosing where each VM lives on your network, so three addresses that work on one machine may already be taken on another. Skip the specific numbers below and pick your own free addresses in your subnet.

Pick three free addresses

Fill in your subnet's first three octets once, then pick three host numbers outside your router's DHCP range (check your router settings, or stay above .100 as a rule of thumb).

VMStatic IP
controller-001<your-subnet>.101 e.g. 192.168.137.101
worker-node1<your-subnet>.102 e.g. 192.168.137.102
worker-node2<your-subnet>.103 e.g. 192.168.137.103

Check the addresses you picked aren't already taken — replace the example with your own three addresses:

PowerShell — replace with your addresses
ping <your-subnet>.101
ping <your-subnet>.102
ping <your-subnet>.103

Timeouts or "destination host unreachable" mean the address is free. The rest of this guide uses 192.168.137.101/102/103 as an example — wherever you see those addresses in later steps, substitute the three you picked here.

Copy and run the script

Swap in the three addresses you picked above — the ones below (.101/.102/.103 on 192.168.137.x) are only an example.

PowerShell — example addresses, use your own
multipass transfer .\set_static_ip.sh controller-001:/home/ubuntu/
multipass transfer .\set_static_ip.sh worker-node1:/home/ubuntu/
multipass transfer .\set_static_ip.sh worker-node2:/home/ubuntu/

multipass exec controller-001 -- bash set_static_ip.sh 192.168.137.101
multipass exec worker-node1 -- bash set_static_ip.sh 192.168.137.102
multipass exec worker-node2 -- bash set_static_ip.sh 192.168.137.103
Each run ends with only the static address on enp0s8
>>> Static IP : 192.168.137.101/24
>>> Result:
3: enp0s8: ...
    inet 192.168.137.101/24 ... scope global enp0s8

If you saved or edited the script on Windows and bash complains about \r, strip the Windows line endings first: multipass exec <vm> -- sed -i 's/\r$//' set_static_ip.sh. The download button on this page already uses the right line endings.

Restart and confirm the addresses stick

PowerShell — example address, use your controller's
multipass restart --all
multipass list
multipass exec worker-node1 -- ping -c 2 192.168.137.101
multipass exec worker-node2 -- ping -c 2 192.168.137.101

Don't go further until multipass list shows the three addresses you picked (.101, .102, .103 in the example above) after the restart, and both pings succeed. If an old DHCP address is still listed on enp0s8, restart that VM once more.

Why this works: Multipass defines the bridged interface in /etc/netplan/50-cloud-init.yaml under the ID extra0, matched by MAC address. The script adds a second file with the same ID and DHCP turned off, and netplan merges the two, so cloud-init's file stays untouched. Windows shares this subnet through Internet Connection Sharing and doesn't know about your static addresses, so avoid addresses another device already uses.

Copy the scripts

PowerShell on Windows

From the root of your cloned Git repository, copy prep_node.sh to all three VMs and init_controller.sh to the controller only.

PowerShell
multipass transfer .\prep_node.sh controller-001:/home/ubuntu/
multipass transfer .\prep_node.sh worker-node1:/home/ubuntu/
multipass transfer .\prep_node.sh worker-node2:/home/ubuntu/
multipass transfer .\init_controller.sh controller-001:/home/ubuntu/

Prep all three nodes

All 3 VMs

The script turns off swap, sets the kernel network options, installs containerd and the Kubernetes tools (v1.32), and tells kubelet to use the enp0s8 address instead of 10.0.2.15.

PowerShell
multipass exec controller-001 -- bash prep_node.sh
multipass exec worker-node1 -- bash prep_node.sh
multipass exec worker-node2 -- bash prep_node.sh
Check the first and last lines of each run
>>> Using node IP: 192.168.137.101
...
=== NODE PREP COMPLETE (IP: 192.168.137.101) ===

The node IP must be the static enp0s8 address you set in step 3 for that VM (.101/.102/.103 in this guide's example), never 10.0.2.15.

Start the controller

controller-001

This runs kubeadm init with the real IP, sets up kubectl, and installs Calico bound to the right subnet. It ends by printing the join command for the workers.

PowerShell
multipass exec controller-001 -- bash init_controller.sh
Copy the last line of the output — the IP is your controller's
kubeadm join 192.168.137.101:6443 --token <token> \
    --discovery-token-ca-cert-hash sha256:<hash>

The script reads the controller's own enp0s8 address, so the IP in your output will already be the one you set in step 3 — 192.168.137.101 here is just this guide's example.

Lost the command, or the token expired (24 hours)? Print a new one with multipass exec controller-001 -- sudo kubeadm token create --print-join-command.

Join the workers

worker-node1 and worker-node2

Run the join command on each worker with sudo, using the full command step 6 printed — it already carries your controller's real IP, not the example below.

PowerShell — example, use step 6's actual output
multipass exec worker-node1 -- sudo kubeadm join 192.168.137.101:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>

multipass exec worker-node2 -- sudo kubeadm join 192.168.137.101:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>
Each join ends with
This node has joined the cluster

Use kubectl from Windows

PowerShell on Windows

So far every command went through multipass exec. With a copy of the cluster's kubeconfig on Windows, you can run plain kubectl from PowerShell instead. The kubeconfig holds the API address, the certificates, and the default context.

Install kubectl

Already installed it in Install prerequisites? Skip to the next section. Otherwise:

PowerShell
winget install -e --id Kubernetes.kubectl
kubectl version --client

Open a new PowerShell window afterwards so kubectl is on your PATH. kubectl must be within one minor version of the cluster (v1.32). If winget installs something much newer, download the matching version instead:

PowerShell
mkdir C:\k8s -Force
curl.exe -L -o C:\k8s\kubectl.exe https://dl.k8s.io/release/v1.32.0/bin/windows/amd64/kubectl.exe
$env:Path += ";C:\k8s"

Check that Windows can reach the API server

PowerShell — example address, use your controller's
Test-NetConnection 192.168.137.101 -Port 6443
What you should see
TcpTestSucceeded : True

Copy the kubeconfig from the controller

Pipe the file through multipass exec. The -Encoding ascii part matters, because PowerShell 5.1 otherwise saves the file as UTF-16 and kubectl can't read it.

PowerShell
mkdir C:\k8s -Force
multipass exec controller-001 -- sudo cat /etc/kubernetes/admin.conf | Out-File -Encoding ascii C:\k8s\admin.conf
Get-Content C:\k8s\admin.conf -TotalCount 5

multipass transfer can fail here with "cannot set permissions for local file". That's a Windows permissions quirk in Multipass, so use the command above instead.

Point kubectl at the file

PowerShell
# this window only
$env:KUBECONFIG = "C:\k8s\admin.conf"

# every new window from now on
[Environment]::SetEnvironmentVariable("KUBECONFIG", "C:\k8s\admin.conf", "User")

If kubectl reports localhost:8080 or "no context exists", it isn't reading your file. KUBECONFIG resets in every new window unless you set it permanently, and a typo in the path (like admin.confg) has the same effect. Check with echo $env:KUBECONFIG and Test-Path C:\k8s\admin.conf.

Check and set the context

PowerShell
kubectl config get-contexts
kubectl config use-context kubernetes-admin@kubernetes
kubectl get nodes -o wide

Optionally give the context a friendlier name and a default namespace:

PowerShell
kubectl config rename-context kubernetes-admin@kubernetes multipass-k8s
kubectl config use-context multipass-k8s
kubectl config set-context --current --namespace=default
Already have other clusters in your kubeconfig?

Merge instead of replacing, so you can switch clusters with kubectl config use-context.

PowerShell
$env:KUBECONFIG = "$HOME\.kube\config;C:\k8s\admin.conf"
kubectl config view --flatten | Set-Content -Encoding ascii $HOME\.kube\merged
Copy-Item $HOME\.kube\config $HOME\.kube\config.bak
Move-Item -Force $HOME\.kube\merged $HOME\.kube\config
Remove-Item Env:KUBECONFIG
kubectl config get-contexts

Try it: open nginx in your browser

PowerShell
kubectl create deployment nginx --image=nginx --replicas=2
kubectl expose deployment nginx --port=80 --type=NodePort
kubectl get svc nginx
Note the port after 80:
NAME    TYPE       CLUSTER-IP     PORT(S)        AGE
nginx   NodePort   10.x.x.x       80:31234/TCP   5s

Open http://<any-node-IP>:31234 in your Windows browser, using any node's static IP from step 3 (e.g. 192.168.137.102 in this guide's example) and your own NodePort. You should see the nginx welcome page. Clean up when done:

PowerShell
kubectl delete service nginx
kubectl delete deployment nginx

This kubeconfig gives full admin access to the cluster. Keep it private and never commit it to git. If a VM's IP changes after a restart, copy the file again.

Snapshot the cluster

PowerShell on Windows

Once all three nodes are Ready, save the state so you can roll back after a mistake. Multipass can only snapshot stopped VMs, and the three nodes belong together, so stop them all and give every snapshot the same name. Stop the workers first and the controller last.

PowerShell
multipass stop worker-node1 worker-node2
multipass stop controller-001

$d = Get-Date -Format "yyyy-MM-dd"
$c = "kubeadm cluster, 3 nodes Ready, taken " + (Get-Date -Format "yyyy-MM-dd HH:mm")

foreach ($vm in "controller-001","worker-node1","worker-node2") {
    multipass snapshot $vm --name "cluster-ready-$d" --comment $c
}

multipass start --all

That creates names like cluster-ready-2026-09-21. If you might snapshot twice in one day, use -Format "yyyy-MM-dd-HHmm" so the names don't clash. Snapshot names can contain letters, digits and hyphens, but not underscores, spaces or colons.

List your snapshots

PowerShell
multipass list --snapshots
multipass info controller-001 --snapshots

Restore all three together

PowerShell
multipass stop --all

foreach ($vm in "controller-001","worker-node1","worker-node2") {
    multipass restore "$vm.cluster-ready-2026-09-21" --destructive
}

multipass start --all
kubectl get nodes

Restoring discards each VM's current state, so make sure that's what you want. Nodes can take a minute or two to show Ready again.

Delete a snapshot you no longer need

PowerShell
multipass delete controller-001.cluster-ready-2026-09-21 --purge

A second useful snapshot point is after step 5 (all nodes prepped, before kubeadm init). Use --name "prepped-$d" and you can redo the cluster without reinstalling packages.

Snapshots live on the same disk as the VMs, so they aren't a backup: deleting a VM with --purge deletes its snapshots too. If multipass snapshot reports an error about driver support, snapshots aren't available with your VirtualBox setup.

Troubleshooting

Workers can't ping the controller

Wi-Fi adapters often block bridging, but a wired adapter like yours usually works. Confirm each VM has an enp0s8 address with multipass exec <vm> -- ip -4 addr. If enp0s8 is missing, the VM was created without --network Ethernet. Delete and recreate it. Then check that Windows Firewall isn't blocking ICMP on the bridged adapter.

prep_node.sh says it can't detect an IP on enp0s8

Run multipass exec <vm> -- ip -4 addr and look for the non-10.0.2.15 address. If it lives on a different interface name, pass that VM's own static IP manually: bash prep_node.sh <that-VMs-static-IP> (e.g. bash prep_node.sh 192.168.137.101). If init_controller.sh reports the same problem, the interface name is hard-coded as enp0s8 at the top, so edit it there.

kubeadm join: connection refused or timeout

The join command must point at the controller's enp0s8 address on port 6443. "Connection refused" against 10.0.2.15 means you're using the NAT address, which every VM shares. Confirm the API server is up with multipass exec controller-001 -- sudo ss -tlnp | findstr 6443, or from inside the controller sudo ss -tlnp | grep 6443.

Token expired or join command lost

Tokens last 24 hours. Print a fresh command: multipass exec controller-001 -- sudo kubeadm token create --print-join-command.

A node is still NotReady after 5 minutes

Find the stuck pod with kubectl get pods -A -o wide, then run kubectl describe pod -n calico-system <pod> for the reason. On the affected worker, check sudo journalctl -u kubelet -n 30 --no-pager. Image pulls are the usual cause and resolve on their own.

The cluster broke after restarting the VMs

The cluster is tied to the VMs' IP addresses. If multipass list shows different addresses than when you built it (for example the controller moved from .63 to .22), the API server certificate no longer matches and kubectl times out. Fix it once: set static IPs in step 3, wipe Kubernetes with the reset commands below, then redo steps 5 to 9.

multipass transfer: "cannot set permissions for local file"

This is a Windows permissions quirk in Multipass. The file may still have copied, so check with Get-Content C:\k8s\admin.conf -TotalCount 5. If it's missing or empty, use the multipass exec ... cat command from step 9, which avoids the problem.

kubectl: connection to localhost:8080 refused

kubectl found no kubeconfig, so it fell back to its default. KUBECONFIG is either unset in this window or points at a path that doesn't exist. Run echo $env:KUBECONFIG and Test-Path C:\k8s\admin.conf, then set $env:KUBECONFIG = "C:\k8s\admin.conf". Set it permanently with [Environment]::SetEnvironmentVariable("KUBECONFIG", "C:\k8s\admin.conf", "User") and open a new window.

kubectl: no context exists with the name "kubernetes-admin@kubernetes"

The file kubectl is reading doesn't contain that context. Check kubectl config get-contexts to see what's loaded, and confirm the file name has no typo (dir C:\k8s). If you renamed the context earlier, use the new name.

The static IP didn't apply

Run multipass exec <vm> -- sudo cat /etc/netplan/60-static-extra0.yaml and confirm it exists and has the right MAC. Then sudo netplan generate shows any syntax error. If the old DHCP address is still on enp0s8, run multipass restart <vm>. Also confirm the ID in /etc/netplan/50-cloud-init.yaml is extra0, because the script relies on it to merge the two files.

kubectl on Windows can't read the config, or shows odd characters

The file was probably saved as UTF-16. Re-create it with Out-File -Encoding ascii as shown in step 9. Also confirm $env:KUBECONFIG points at the right file.

kubectl on Windows times out

Run Test-NetConnection <your-controller-IP> -Port 6443. If it fails, the Windows host can't reach the bridged network, or the controller's IP changed. In the second case, look up the new IP, then copy the kubeconfig again.

Reset and clean up

Redo a worker's join

PowerShell
multipass exec worker-node1 -- sudo kubeadm reset -f

Redo the controller's init

PowerShell
multipass exec controller-001 -- sudo kubeadm reset -f
multipass exec controller-001 -- sudo rm -rf /etc/cni/net.d /home/ubuntu/.kube

Wipe Kubernetes but keep the VMs

PowerShell
multipass exec worker-node1 -- sudo kubeadm reset -f
multipass exec worker-node2 -- sudo kubeadm reset -f
multipass exec controller-001 -- sudo kubeadm reset -f
multipass exec controller-001 -- sudo rm -rf /etc/cni/net.d /home/ubuntu/.kube
multipass exec worker-node1 -- sudo rm -rf /etc/cni/net.d
multipass exec worker-node2 -- sudo rm -rf /etc/cni/net.d
multipass restart --all

Then redo steps 6 to 9. Only redo step 5 (prep_node.sh) if the VMs' IP addresses changed.

Delete the whole cluster

PowerShell
multipass delete --purge controller-001 worker-node1 worker-node2
